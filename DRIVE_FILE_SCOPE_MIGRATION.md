# Google Drive OAuth scopes и настройка Google Picker

Это описание текущей архитектуры основной ветки `main`, а не отдельной экспериментальной ветки. Приложение использует `drive.readonly`, `drive.appdata` и `drive.file`; широкое разрешение `drive` не требуется и не должно возвращаться.

## Одноразовая настройка Google Cloud

1. Включите [Google Picker API](https://console.cloud.google.com/apis/library/picker.googleapis.com) в том же Google Cloud project, где находится OAuth client сайта.
2. Создайте отдельный browser API key.
3. Ограничьте ключ по HTTP referrers: `https://tssrkt.github.io/*` и `http://localhost:8000/*` для локальной проверки.
4. Ограничьте API key только Google Picker API. Не помещайте OAuth client secret во frontend.
5. Для локальной проверки добавьте `http://localhost:8000` в Authorized JavaScript origins OAuth client.
6. Укажите публичный ограниченный ключ в `GOOGLE_PICKER_API_KEY` в `js/config.js`. Секрет не хранится в репозитории.

Если ключ не настроен, приложение должно безопасно отказывать в Drive-операциях, которым требуется Picker.

## Поведение и ограничения миграции

- Старые OAuth-сессии не переиспользуются молча после смены scope; пользователь должен войти снова и выдать новые разрешения.
- Сохранённая корневая папка один раз выбирается в Picker для авторизации точного объекта через `drive.file`.
- `drive.readonly` позволяет читать существующие каталоги; перед изменением или удалением конкретного объекта приложение должно получить необходимую авторизацию для этого объекта.
- Выбор папки не означает автоматическую авторизацию всех вложенных папок. Для изменения разрешений вложенная папка должна быть авторизована отдельно.
- Созданные приложением файлы каталога и явно выбранные папки могут сохраняться как локальные подсказки для UX, но Google Drive остаётся источником истины и может отклонить операцию.
- `drive.file` не является абсолютным запретом на удаление выбранных/авторизованных объектов. Безопасность также зависит от того, какие операции приложение отправляет в Drive API; не добавляйте DELETE для книжных файлов без отдельного обоснования.

## Проверка после настройки

1. Войти отдельным тестовым Google-аккаунтом.
2. Убедиться, что OAuth использует `drive.readonly drive.appdata drive.file` и не запрашивает `drive`.
3. Выбрать корневую папку и подтвердить её в Picker.
4. Опубликовать каталог, обновить метаданные книги и проверить чтение каталога из аккаунта друга.
5. Отозвать публикацию и проверить, что каталог больше не опубликован.
6. Изменить разрешение вложенной папки и проверить ограниченный доступ.
7. Убедиться, что приложение не изменяет не выбранный пользователем объект.
8. Повторить после перезагрузки и входа под другим аккаунтом.

Совместимость реального OAuth/Picker и авторизации объектов Drive требует живого тестового аккаунта и ограниченного API key. Unit-тесты не доказывают серверное поведение Google для каждого объекта.
